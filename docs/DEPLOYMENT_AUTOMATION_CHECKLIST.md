# PokerAttack deployment automation implementation checklist

Source of truth: [deployment automation plan](DEPLOYMENT_AUTOMATION_PLAN.md). Created 2026-11-15.

Implement separate GitHub Actions client/SWA and server/ACR/Linode delivery, preserve maintenance and promotion gates, and create one shared **Linode Docker Containers** dashboard. This is an executable work checklist; creating it does not execute its tasks. All implementation items start unchecked, including work that may already exist but still requires verification.

## How an agent must use this checklist

1. Read the plan, applicable `AGENTS.md` instructions, current release README, and the progress/evidence entries below. Inspect current files and live state before relying on historical findings.
2. Work in phase order and obey dependencies. Select the first incomplete eligible task; record its ID as current before changing anything. If a required input is unavailable, record the precise blocker and continue only with independent eligible work. Do not spawn other agents unless separately instructed.
3. Use `[ ]` for incomplete and `[x]` only after the stated completion condition is verified. A task with code but no required live verification stays unchecked. Record `IN_PROGRESS`, `BLOCKED`, or `FAILED` in the phase table/journal; none means completed.
4. After each task, add an evidence entry, update its checkbox and phase status, and name the next eligible task. Record failed checks and corrective actions; do not discard failure evidence when a retry succeeds. Reopen completed tasks if later changes invalidate their evidence.
5. Every completed task needs a UTC timestamp, tested source identity, verification method/result and evidence reference. Use source SHA plus relevant file hashes for uncommitted changes. Never represent a local working tree as a published image's provenance.
6. Store sanitized reports under `docs/deployment-evidence/` when created, with names containing the task ID. Keep large test artifacts in durable CI storage and link their run/artifact identities. Record a secure storage reference for sensitive evidence, never its contents. Do not publish env files, SSH keys, credentials, private gameplay payloads or unredacted Docker inspection output.
7. On resuming, reconcile journal/checkmarks with GitHub runs, host state and artifacts. After uncertain SSH/deployment outcomes, inspect state before retrying. A checked implementation task is not a claim that a later release succeeded.
8. This request authorizes checklist creation only. A later instruction to implement supplies execution scope; use that instruction and existing authorization without repeatedly asking for routine steps. Preserve the plan's fresh match-reset acknowledgment and explicit promotion decision for real releases. Complete build/rehearsal work before presenting those concrete release decisions.

The checklist does not reintroduce recurring browser monitors, application-wide telemetry, alert/contact-point setup, extra observation windows or automatic rollback based on Grafana charts. Deployment-time gameplay verification remains required. Grafana availability is not an application readiness dependency.
